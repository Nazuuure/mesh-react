# Контур · CPS Group
Локальный прототип mesh-доставки для хакатона RWB × ПГТУ. Четыре роли используют одну базу и переключаются в шапке. Режим ПВЗ дополнительно выбирает конкретный пункт. Цены, расстояния, спрос, расписание и начисления демонстрационные.

## Запуск организатором
Распакуйте архив, откройте терминал в папке с compose.yaml. Требуется Docker с Compose. Для первой сборки нужен интернет для образов и драйвера pg.

```sh
docker compose up --build
```
Откройте http://localhost:8000. Данные в постоянном томе PostgreSQL. Остановка: `docker compose down`. Сброс из интерфейса: диспетчер → управление демонстрацией → восстановить демоданные. Сервер публикуется только на loopback.

Без Docker при наличии Node.js 24: `node server.mjs`, тот же адрес. Этот режим сохраняет состояние в локальной SQLite. Установка npm-пакетов не нужна. Тесты в обоих режимах: `node --test test.mjs` или `docker compose exec web node --test test.mjs`.

## Двухминутный показ
1. Покупатель. Выберите Заречный и закажите наушники Studio. Они есть в Центральном. Нажмите «Доставить в выбранный ПВЗ».
2. Продавец. Отправьте ещё две упаковки наушников из Центрального в Заречный. Три коробки готовы к общему рейсу.
3. Диспетчер. Отметьте обе заявки. Прочитайте цену одной коробки. Можно сравнить рейс с отправкой через хаб. Запустите робота, завершите погрузку, подтвердите прибытие и разгрузку.
4. Сотрудник Заречного. Выдайте заказ. Откройте экономику ПВЗ, затем переключитесь на продавца и покажите прибыль. После возврата пересчитываются результат и остаток.

## Сценарий с хабом и промежуточным ПВЗ
Закажите рюкзак City в Заречный. В диспетчерской выберите магистральную заявку, укажите Парковый и запросите приёмку. Переключитесь на сотрудника Паркового и отклоните партию. Посмотрите нового адресата в истории диспетчера. Сотрудник нового ПВЗ принимает партию, это моделирует её прибытие. Вернитесь к покупателю. При согласии забрать товар в текущем ПВЗ заказ готов к выдаче там. При отказе появляется задача роботу до исходно выбранного адреса. Если промежуточный пункт совпал с выбранным адресом, товар сразу готов к выдаче.
Для поставки продавца создайте карточку с партией на хабе и заявку на нужный ПВЗ. При приёмке в промежуточном ПВЗ следующий участок создаётся автоматически. Каждая упаковка может быть зарезервирована один раз. Физический остаток списывается при выезде, целевой склад заранее резервирует объём. Сотрудник может уменьшить ёмкость только до уже занятого и обещанного объёма. После отказа всех подходящих пунктов заявка ожидает места и доступна для повторного согласования.

## Модель
- Литраж вводится продавцом отдельно от габаритов. Все размеры в сантиметрах. Свободный объём = вместимость − физический объём − обещанные поставки. Спрос = начальная история категории + реальные тестовые заказы по выбранному покупателем ПВЗ. Цвета и координаты относятся к условной схеме каждого города.
- Источник заказа: нужный пункт, затем ближайший с остатком в том же городе, хаб, другой город. «Рядом» означает до 4 единиц условной сетки. Сроки под кнопкой ориентировочные. Для другого города перевозка моделируется через хаб. Цены товаров от маршрута не меняются.
- Магистральные заявки объединяются по городу, робот собирает заявки одного исходного ПВЗ и обходит пункты назначения по правилу ближайшей следующей остановки. Разгрузка завершает весь рейс. Порог для демонстрации — 3 упаковки, либо одна после суток ожидания. Предел 80 л. Для партии сверх лимита или срочного заказа диспетчер выбирает хаб. Сбой возвращает груз на базу и снова открывает заявки. Небольшую партию можно отправить после перевода дня в диспетчерской.
- Модель отдельного рейса: 360 ₽ / число коробок. Базовый хаб — 80 ₽ за единицу. Порог запуска и экономическая окупаемость различаются. Цены рейса и хаба в очереди сравнивают транспортную часть. В итогах WB дополнительно вычитаются выплаты ПВЗ. Автоматического выбора по полной себестоимости нет, решение принимает диспетчер.
- Учебная модель начислений на выданный заказ: хранение 0,50 ₽ × литры × дни с оприходования карточки; операции 22 ₽; затраты труда ПВЗ 12 ₽. Начисление относится к выдающему ПВЗ. Партии и выплаты между промежуточными складами отдельно не распределяются. Себестоимость продавца 60% цены, комиссия 10%. Profit продавца = продажа − себестоимость − комиссия − начисления за ПВЗ − перевозка. Эффект WB = базовые 80 ₽ − начисления ПВЗ − перевозка. Возврат отменяет продажную маржу и добавляет 15 ₽ обратной обработки. Эти ориентиры предназначены для показа механики.
- Долгое хранение: перед выдачей нажмите «Следующий день» несколько раз. Сравните начисление и экономию WB для аналогичного заказа. Возврат после выдачи выполняет сотрудник пункта. Повторная выдача или возврат отклоняются.

## Архитектура и передача
Node.js 24, HTTP API, обычный JavaScript и CSS, PostgreSQL в Docker. API: GET /health, GET /api/state, POST /api/actions. Каждая команда передаёт объект с type, version и полями формы. Ответ — новое состояние или ошибка. Версия блокирует повторные клики и устаревшие формы. Один процесс сериализует изменения и атомарно записывает компактный снимок демостенда. Интерфейс обновляет данные при смене роли, фокусе окна и во время простоя.

Для сдачи архив содержит Git-репозиторий с историей. Команда может отправить его в собственный Git-сервис и передать ссылку организаторам.

## План пилота
Одна пара городских ПВЗ, затем несколько точек одного города. Считать поток по часам, фактическую загрузку рейса, полную стоимость выданного заказа относительно хаба, срок до выдачи и число отказов в приёмке. Пример оценки: 50 ПВЗ × 100 заказов/сутки × 8 записей на заказ = 40 000 операций/сутки, около 0,46 записи/с в среднем и 4,6 при десятикратном пике. Это оценка, а не результат нагрузочного теста. Для сети заменить общий снимок отдельными таблицами и транзакциями по партиям, добавить индексы по городу, статусу и ПВЗ, проверку прав на сервере, журнал событий, метрики задержки и ошибок, резервное копирование и проверку восстановления. Текущий режим без паролей рассчитан на локальную демонстрацию.
